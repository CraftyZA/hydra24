# Hydra24

hydra24.co.za. It was split out of the MouseScoring project and still runs on
MouseScoring's VPC and Postgres instance to keep AWS costs low.

## Layout

- `iac/` - Terraform. Own state: `s3://mousescoring-terraform-state/hydra24/terraform.tfstate`
  (same bucket and DynamoDB lock table as MouseScoring, different key).
- `backend/` - Quarkus (GraalVM native) Lambda behind an HTTP API (`iac/api.tf`),
  plain JDBC with Flyway migrations. Verifies Cognito ID tokens itself
  (`JwtVerifier`, keys from `iac/jwt_trust.tf`).
- `ui/` - static site, S3 + CloudFront (OAC). Each landing-menu section has its
  own folder holding its page and sub pages, e.g. `ui/events/events.html`,
  `ui/events/calendar.html`. The back button works out the parent page from
  this layout. Shared JS lives in `ui/common/`. Sign-in is `ui/common/auth.js`
  (Cognito hosted UI, PKCE). `ui/common/auth-config.js` is generated by
  `deploy.sh` and not committed. The CSP comes from CloudFront (`iac/site.tf`),
  not from meta tags. Use root-absolute
  paths (`/styles.css`, `/images/...`) so pages work at any depth.
- `docs/` - design notes. Read `docs/shared_infrastructure.md` before touching
  anything network or database related.
- `deploy.sh` - builds the backend, applies `iac/`, writes the auth config,
  syncs `ui/` to S3, invalidates CloudFront.

## Shared infrastructure rules

MouseScoring **owns** the VPC, private subnets, security groups
(`mousescoring-lambda-sg`, `mousescoring-rds-sg`, `mousescoring-endpoints-sg`),
VPC endpoints and the RDS instance `mousescoring-postgres`. This project:

- Reads them only through data sources in `iac/shared.tf`. Never declare,
  import or modify them here.
- May add its own standalone resources that point at them, such as
  `aws_vpc_security_group_ingress_rule` into the RDS (5432) or endpoints (443)
  group from a Hydra24-owned Lambda SG.
- Must never require a change in the MouseScoring repo just to work, except when
  a shared resource itself has to change. Make that change in MouseScoring.

Postgres: use the separate `hydra24` database with its own `hydra24_app` role.
Do not use a schema in MouseScoring's `3dscores` database, and do not use the
RDS master credentials in the app.

Cognito: Hydra24 has its own user pool, defined in `iac/`. Nothing is shared
with MouseScoring's pools.

## Working preferences

- Don't run `sudo`. Give the user the command to run.
- Don't run `terraform apply` or `deploy.sh` unless asked. `terraform plan`
  is fine.

## Coding standards

- **Mobile first.** Design for a phone screen first, then let it scale up.
  Pages fit one screen with no scrolling. Content shrinks to fit (see
  `ui/styles.css`).
- **DRY / reuse.** Don't repeat code. Before writing something new, look for an
  existing component, module or Terraform resource pattern and reuse it. Build new
  ones to be reusable: small, parameterised, no page- or caller-specific
  assumptions baked in. For example, put shared UI in `ui/common/`.
- **SOLID** (Robert C. Martin): single responsibility, open/closed, Liskov
  substitution, interface segregation, dependency inversion.
- **Clean Code** (Robert C. Martin): intention-revealing names, small functions
  that do one thing, no side effects hidden behind names, few arguments, no dead
  or commented-out code, and comments only where the code can't explain itself.
  Leave code cleaner than you found it.
- Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify. 
- **Security first.**
  - No secrets in the repo. Use Secrets Manager or SSM.
  - Give IAM and security groups least privilege.
  - Validate input at the server. Use parameterised SQL only.
  - Encode output, with no `innerHTML` for untrusted data.
  - Verify JWTs in the backend.
  - Keep dependencies pinned and current.
